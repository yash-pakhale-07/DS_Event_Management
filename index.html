Algorithms & Data Structures Used in this System

Singly Linked List O(n) / O(1)

Stores confirmed participants. Each node holds { id, name, email, next }. Maintains both head and tail pointers. Appending is O(1) (duplicate ID check requires an O(n) linear search first). Deletion with pointer bypass is O(n).

Linear Search O(n)

Walks the linked list starting from head. searchById(id) looks for exact matching ID; searchByName(query) performs a case-insensitive substring match. Both have O(n) time complexity.

Linked Queue (FIFO) O(1)

Custom singly linked queue with front and rear pointers. enqueue() and dequeue() run in O(1). Powers the event waitlist when the participant limit is reached.

Linked Stack (LIFO) O(1)

Custom singly linked stack tracking action snapshots (action type, participant data, and prevId for exact position restoration). push() and pop() are O(1).

Linked List Merge Sort O(n log n)

Divides the list using the slow/fast pointer technique (tortoise and hare) in O(n), sorts recursively, and merges two sorted sub-lists by rewiring node pointers without auxiliary arrays. Re-points the tail pointer upon completion.

Form Submitted: Input Validation

Form Handling O(1)

Step 2

Duplicate Check: Linear Search

Linear Search O(n)

Walks node-by-node from the linked list's head comparing existing participant IDs against the candidate ID to guarantee uniqueness.

head ➔ [ID: 101] ➔ [ID: 102] ➔ Check: curr.id === inputId ? ➔ null
Step 3

Capacity Verification

State Condition O(1)

Evaluates whether the linked list length < eventCapacity to determine if the registrant qualifies for immediate confirmation or the waitlist.

Registered Count (length) < Capacity (N) ➔ TRUE: Branch 4a | FALSE: Branch 4b
Step 4a

Space Available: Linked List Tail Append

Singly Linked List O(1)

Utilizes the tracked tail pointer to append the new node in constant time via tail.next = newNode; tail = newNode; without full traversal.

... [Prev Node] ➔ [Old Tail] ➔ [New Node] (New Tail) ➔ null
Step 4b

Event Full: FIFO Waitlist Enqueue

Linked Queue O(1)

If the event is full, the participant is enqueued at the rear of the waitlist queue using the rear pointer: rear.next = node; rear = node;.

front ➔ [W1] ➔ [W2] ➔ [W3 New Registrant] (rear) ➔ null
Step 5

Record Action: Stack Push

Linked Stack O(1)

Pushes an action snapshot onto the top of the LIFO undo stack containing the operation type, participant payload, and predecessor node reference (prevId).

top ➔ [Action: REGISTER / CANCEL] ➔ [Prior Action] ➔ null
Step 6

Searching: Linear Search by ID or Name

Linear Search O(n)

Walks the list sequentially starting from head. Compares exact IDs or performs case-insensitive substring checks, collecting matches without using any Hash Maps.

head ➔ [Alice] ➔ [Bob (Match Highlighted!)] ➔ [Charlie] ➔ null
Step 7

Sorting: Linked List Merge Sort

Divide & Conquer O(n log n)

Splits list into halves with slow/fast pointers in O(n), recursively sorts each half, merges them by rewiring next pointers, and re-points tail to the last node.

[Sublist L] + [Sublist R] ➔ (Compare & Splice) ➔ [Sorted Linked List] ➔ tail reset ✓
Step 8

Cancellation: Search & Node Bypass

Singly Linked List O(n)

Locates the target node using linear search while tracking prev. Bypasses the node via prev.next = curr.next and accurately updates head and tail.

[prev Node] ───(bypasses [curr Cancelled])───➔ [curr.next Node]
Step 9

Waitlist Promotion: FIFO Dequeue

Linked Queue O(1)

When a spot opens due to cancellation, the participant at front is dequeued in O(1) and automatically appended into the confirmed participants list.

dequeue(front) ➔ [First Waitlisted Person] ➔ registerParticipant() ➔ Confirmed List ✓
Step 10

Undo: Stack Pop & Inverse Action

Linked Stack O(1)

Pops the last action from top in O(1). Restores cancelled nodes to their original position using prevId, and returns any auto-promoted waitlist member to the queue front.

pop(top) ➔ [Inspect Action Type] ➔ insertAt(prevId) / prepend(front)
